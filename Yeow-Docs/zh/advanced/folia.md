# Folia 支持（实验性）

> **状态：实验性。** 核心链路（调度器/任务/事件/命令/定时器/PDC/文本/权限）已在 Folia 1.21 实机验证。**任务与事件已与 Paper 全对齐**（任务与 Paper 全部 224 个 case 严格一致；事件 41 个 Bukkit 事件 + permissionCheck 生态钩子，2026-08-13）。Paper 系（Paper/Purpur/Leaf 等）的官方实现仍是 `yeow-runtime`。

## 实验性说明

Folia 是 Paper 的分支，核心差异是**区域化多线程**（regionized multithreading）：没有全局主线程，世界按区块划分区域（region），每个 region 由独立线程并行 tick。这直接冲击了 Yeow 原本建立在"单主线程"上的同步桥模型，因此 Folia 支持是一个**独立的运行时实现**，而非对 Paper 运行的适配。

当前支持范围（与 Paper 任务/事件全对齐，2026-08-13）：

| 类别   | 覆盖                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------------------- |
| 世界   | 方块读写（含 BlockData 状态）、时间/天气/难度/规则（全局状态写入自动路由全局线程）、生成点、生物群系、光照、实体查询/生成、掉落/闪电/爆炸/音效/粒子/区块快照 |
| 玩家   | 属性/位置/传送/消息（MiniMessage）/Title/ActionBar/音效/物品/资源包/权限（含 permissionCheck 生态钩子）等 40+ 操作 |
| 实体   | 属性/自定义名/生命值/发光/无敌/静默/重力/边界盒/乘客/载具/药水效果                                         |
| 数据   | PDC（实体/方块/世界）、Material 注册表查询与静态判断                                                       |
| 事件   | 41 个 Bukkit 事件全对齐（玩家/实体/方块/库存/服务器类）+ `permissionCheck` 生态钩子                       |
| 命令   | 注册/注销/执行/Tab 补全（权限节点注册 PermissionDefault）                                                  |
| Inventory/杂项 | 统一 Inventory（玩家物品栏 / 容器方块 / 自定义箱子界面）、BossBar、Scoreboard（创建受限，见下）、Recipe、Advancement |
| 运行时 | 热重载（dev WS）、定时器、fs/http/assets/service 通道（core 自带）                                        |

已知差异见文末[架构推论](#架构推论)。

## Folia 下 Yeow 的架构

### 分层

```
yeow-runtime/jvm/
├── core/    平台无关引擎（QuickJS、消息桥、插件生命周期、TaskScheduler 契约）——Paper/Folia 共用
├── paper/   Paper 平台实现（PaperScheduler：主线程每 tick 直接消费三级池——恢复拆分前模型，无独立调度线程）
└── folia/   Folia 平台实现（FoliaScheduler + FoliaTasks + 事件/命令桥，独立编写，不与 Paper 共享）
```

引擎（插件加载、JS 线程、消息通道、Service、Profile、权限模型）在 core，两平台零差异；平台差异全部收敛在**调度器**与**任务执行器**。

### Folia 环境的约束（为什么架构长这样）

Folia 实现的区域化多线程是一个巨大的成就，但正由于其内部实现的复杂程度，Folia 能够稳定对上层暴露的并发原语相当匮乏——理解下面四条约束，才能理解 Yeow 调度器为什么是"自己的队列 + 自己的预算 + 自己的超时，Folia 只当传输层"，才能理解 Yeow 的调度循环：

1. **区域线程是不稳定的**：region 与线程的绑定不是契约——区域可动态加载/卸载，线程池可重排，同一区域在不同时刻可能由不同线程 tick。**不能假设"区域 X = 线程 Y"持续成立**。因此 Yeow 的驻留标记每次 cycle 启动都要重新解析（`runCycleOn` 解析 marker → 再投递；world 目标可直接解析，uuid 目标受 AsyncCatcher 约束须经全局线程），不能缓存线程引用
2. **线程是无法标识的**：API 不提供"拿到某任务将运行的线程"（`ScheduledTask` 没有线程 getter，`isOwnedByCurrentRegion` 之外没有身份查询）。**身份判断只能靠归属查询**，不能靠线程名/id 比较
3. **调度队列是无法侵入的**：每个 region 调度器内部的待执行队列是黑盒——不能窥探、计数，也无法判断"任务是否已入队/何时执行"，也无法在区域线程内部拦截任务入队。**Yeow 必须自持全部任务池**（高/普通/低三级），Folia 的调度器只作为投递通道；投递后仅剩**句柄级控制**（取消 / 状态查询，见约束 4）
4. **`Scheduler.run` 投递后的控制是有限的**：任务一经投递即无法**拦截入队**（Folia 队列 FIFO、无优先级钩子），无法**观察执行完成**——region 调度器**没有** retired/完成回调（entity 调度器才有），也无法设置优先级。投递后仅剩句柄级控制：`ScheduledTask.cancel()`（取消未执行任务——Yeow 用于超时兜底时的"幽灵执行"防护）与 `getExecutionState()`（状态查询）。且投递后可能**静默永不执行**（世界卸载/区域停摆）——因此 Yeow 的每次投递都挂 **5s 超时兜底**（补错误 + 回收 in-flight），全部等待都以超时封顶——构造上无死锁

Folia 将区域调度能力对外暴露为黑盒，Yeow 理解并尊重他们的选择，但这为 Yeow 带来了相当大的复杂度。

**可用的原语**（两个核心 + 三个扩展用法，即 Yeow 对 Folia 公开 API 的全部依赖）：

| 原语                                                                                                                     | 用途                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `Bukkit.isOwnedByCurrentRegion(目标)`                                                                                    | 归属查询（核心）——`ownedHere` 的基础：判断"目标区域是否就在当前线程"                                      |
| 目标区域的 Scheduler（`entity.getScheduler()` / `Bukkit.getRegionScheduler()` / `Bukkit.getGlobalRegionScheduler()`）    | 投递通道（核心）——`getScheduler` 闭包的基础：把任务"交给目标区域线程"                                      |
| `Bukkit.isGlobalTickThread()`                                                                                            | 归属查询扩展——GLOBAL 任务在全局瞬态下就地执行（消除二次投递的双跳）                                        |
| `ScheduledTask.cancel()`                                                                                                 | 句柄控制扩展——投递超时兜底时取消未执行任务（防"调用方已报错、任务稍后仍执行"的幽灵执行）                  |
| `getGlobalRegionScheduler().runAtFixedRate`                                                                              | 周期任务扩展——每 tick 定时任务三合一：预算尽重启 / 看门狗（1s 活性）/ 在途投递超时粗粒度扫描              |

Yeow 调度器仅依赖这些原语，自己补齐队列、优先级、预算、**迁移**、超时。迁移机制的目的是，允许 Yeow 调度器在 Folia 的黑盒之外，最大程度上将热点区域的任务执行逻辑截取在本地执行。迁移机制的本质是，Yeow 调度器使用上述原语，配合启发式规则，让调度器随 Scheduler.run() 自动被 Folia 投递至热点区域驻留。

### 调度模型：非阻塞调度器 + 区域驻留

Folia 没有"主线程"可供自旋，Yeow 的同步桥（JS 同步调用要等游戏线程结果）必须重新设计。Folia 调度器遵循以下原则：

- **调度器不是独立线程**：它"驻留"（借宿）在某个 region 的线程上，以**调度循环**（dispatch cycle）的形式运行——循环本身作为任务投递到驻留区域的线程，在区域线程的间隙里消费任务队列
- **非阻塞投递**：调度循环取到任务后**立即投递**（目标在驻留区域 → 就地执行；在其他 region → 经 Folia 调度器异步投递），**绝不等待任务结果**——任务完成时由目标线程回调通知（完成 future、唤醒调度器）。因此多个任务可同时在多个 region **并行执行**（并发上限受 in-flight 限制）
- **JS 同步语义保持**：插件 JS 线程仍在 `future.get` 上等待结果——等待发生在 **JS 线程**，不占用调度器

#### 任务类型三函数契约

调度器**对任务类型零认知**——每个任务类型（按家族共享实现）只提供三件事（内聚在 `FoliaTasks`）：

| 函数                   | 作用             | 说明                                                                                                                                                               |
| ---------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ownedHere(params)`    | 当前线程归属判断 | **直接基于原始参数判定**（不经 key 反推）；调度器据此决定就地执行还是投递                                                                                          |
| `getScheduler(params)` | 目标调度句柄     | `DispatchTarget{ marker, run }`：marker 为纯字符串驻留标记（任意线程可计算）；run 为**惰性调度闭包**（构造零 Bukkit 调用，投递时才在全局线程解析实体并调度到目标） |
| `execute(params)`      | 任务本体         | 与 Paper 侧任务实现对应                                                                                                                                            |

调度器只消费这三件事；任务家族内部的实体/世界/区块坐标解析全部封装在对应实现里。新增任务类型时三个函数同步实现对应分支。

#### 调度循环（dispatch cycle）

```
驻留区域 X 的线程上运行调度循环:
  队列非空 → 持续处理:
    ├─ 事件/补全模式激活 → 退出（事件线程接管）
    ├─ in-flight 任务数 ≥ 上限(默认 100) → 退出（任务完成回调唤醒）
    ├─ 预算尽（物理时间）→ 退出（保持占位，每 tick 定时任务在下一个 tick 边界重启，等待 ≈ 窗口剩余 ~30ms）
    ├─ 取任务 → ownedHere(params) 为真（或 GLOBAL 任务且已在全局线程）→ 就地执行（微秒级，不占 in-flight）
    │          否则 → B 路径：getScheduler().run 投递（in-flight++；GLOBAL 投全局，不参与迁移统计）
    └─ 连续两次非本区域任务 → 让出驻留标记（等待被抢占，见迁移机制）
  队列空 → 阻塞等待 `folia.scheduler-idle-wait-us`（默认 2000us）新任务进入，仍空才退出（submit 提前唤醒）
```

> **空闲等待是 park 而非忙等**：队列空时调度循环在 `cycleLock` 上**阻塞**（`Object.wait`），
> 新任务/任务完成/事件模式结束经 `wake()` `notifyAll` 提前唤醒。此等待要覆盖的是
> **净开销**——JS 线程的往返间隙（complete → JS 唤醒 → 循环体 → submit），常规实测
> **通常 < 50µs**；region 线程满核饱和时 OS 唤醒延迟可能升至 100µs~ms 级，属偶发峰值。
> 不采用忙等自旋，原因：忙等的微秒级响应优势只在低负载下存在，饱和时与 park 差距
> 消失，却持续占用一整个核心；park 释放 CPU，且区域 tick 停顿语义与自旋一致
> （cycle 任务占据区域线程期间 tick 本就暂停）。实际阻塞时长受 OS 定时器粒度影响
> （Windows ~1-15.6ms）可能略超设定值——仍空即退出，仅周期尾一次。
> （参数名 `scheduler-idle-wait-us` 替代早期 `scheduler-spin-us`：语义由自旋改为阻塞等待。）
> **注意：此等待只覆盖"cycle 存活期间的迭代间隙"；JS 线程自身的 OS 唤醒延迟不受此参数控制。**

- **for await 模式的优化**：插件循环里连续同步调用（`for (..) await e.player.xxx`）的目标都在玩家所在 region——调度器驻留该区域后，任务**就地执行**（跳过 region scheduler 排队），循环迭代从"每个任务等一个 tick（~50ms）"降为微秒级。实测（本机，**含 tick 的插件感知总延迟**）：30 次 setBlock 循环 2-6ms（0.1-0.2ms/次）；400 次无间隙持续循环 83-89ms（0.2ms/次）。其中净开销（JS 往返间隙）占比很小——总延迟主要由唤醒 + 调度 + 执行构成
- **预算（物理时间）**：每 50ms 窗口内，调度器活跃的物理时间超过预算（`folia.tick-budget-ms`，默认 20ms）即停止投递，任务暂存队列，窗口滚动后恢复。**预算计物理流逝而非各任务耗时累加**——多区域并行执行时累加会虚增预算，物理时间对并行更友好；同时预算限制 cycle 常驻时长，保证驻留区域至少有 30ms/50ms 的 tick 时间。预算尽时 cycle 保持占位，由**每 tick 定时任务在下一个 tick 边界重启**——等待 ≈ 窗口剩余时间（典型 ~30ms），持续负载下同步调用可能有单次 ≤30ms 抖动，属预算模型固有。**单任务可超支预算**（预算只在任务间检查，任务原子性）——长任务由执行线程自行承担，调度器不打断；重启只由 cycle 完全退出后的定时任务触发，**绝不与在跑任务重叠**
- **in-flight 上限**：同时投递未完成的任务数不超过配置上限（`folia.max-inflight`，默认 100），防止无界投递压垮区域
- **投递超时兜底**：B 路径投递记入在途注册表，由每 tick 周期任务**粗粒度扫描**（每 1s）——5s 未完成则**先 `cancel()` 取消目标任务**（防幽灵执行：调用方已收到超时错误、任务不得稍后仍执行；已完成/已执行的 cancel 为 no-op），再补错误并回收 in-flight。region 调度器**没有** retired 回调（entity 调度器才有），世界卸载/区域停摆时任务可能永不执行；无兜底则 in-flight 永久泄漏 → 达到上限后调度器停摆。**周期任务另有看门狗职责**：cycle 应运行但超 1s 无活动（启动投递被静默丢弃等）→ 强制重启（长任务误触发无害——恢复投递与在跑 cycle 同一线程串行）
- **优先级**：取件唯一规则 = **始终优先更高优先级**（HIGH → NORMAL → LOW，各池 FIFO）；LOW 不被饿死由**提交时自动降级**保证（Paper 同款滑动窗口算法：插件某任务类型 NORMAL 调用频率超过 `demote-threshold`（默认 200 次/秒）即自动降为 LOW，频率回落后自然恢复）

> **配置归属**：`folia.scheduler-idle-wait-us`、`folia.tick-budget-ms`、`folia.max-inflight`、
> `folia.migration-threshold` 为 Folia 专用/语义不同参数，统一放在 `config.yml` 的 `folia:` section，
> 不与 Paper 参数混在顶层。

#### 迁移机制

调度器驻留区域由**热点**决定，迁移基于**让出 + 抢占**：

1. **让出**：调度循环在驻留区域连续遇到 `folia.migration-threshold` 个（默认 2）**非本区域任务**（GLOBAL 不参与）→ 把驻留标记置为"无主"，但**不主动让位**——当前循环继续留在原区域处理（本区域任务仍就地执行）
2. **抢占**：无主状态下，下一个任务（A/B 路径都尝试）执行前**抢占驻留标记**——热点跟随最近任务的目标；被抢占后，cycle 在预算尽/空闲退出重启时经 `runCycleOn` 锚定到新标记（解析失败会清掉过期标记：实体下线/世界卸载后自动释放）

> **迁移阈值调优**：阈值可配置（`folia.migration-threshold`）。**调高**在复杂环境（多人/多插件、热点在区域间频繁摆动）下更稳定——不会因一两个外来任务就反复让出-抢占；但**热点迁移延迟增大**（需要更多连续外来任务才让出，期间外来任务持续走投递）。在合理区间内，此参数对可观测性能的影响不大。默认 2，不建议过高。

迁移机制确保调度器始终贴近任务热点：热点区域的任务就地执行，冷区域的任务投递执行（异步并行）。驻留基准（本机，含 tick 的插件感知总延迟）：setBlock 循环在三组坐标间切换（A → B，相距 1000 块 → 回 A），30 次每组，2-6ms（0.1-0.2ms/次）——驻留保持期间坐标切换不中断就地执行。

#### 事件/补全模式：临时调度器

事件触发（或命令补全请求）时：

- **通用调度器暂停**：调度循环在事件活跃期间退出，计数归零后恢复
- **每个触发事件的 region 线程成为临时调度器**：自旋消费任务队列，**只取本事件派发插件的任务**（纯 L 方案：插件名过滤，不解析归属）。设计依据：事件与（区域, 插件集）一一对应，多事件并发时按插件**天然分流**、互不争抢，且能加快事件处理；**不迁移**
- **事件/补全之间不互斥**：多个事件可在不同 region 同时处理
- **每轮执行上限**（64 个）：事件线程不被事件自身积压拖慢响应（latch 检查在每轮 drain 之间及时退出）
- 每个任务仍交由执行器：目标在当前线程 → 就地执行；否则投递到目标 region（与通用调度器的执行器同一套非阻塞逻辑）

> **纯 L 的取舍**：事件期间其他插件的任务不被取用（cycle 暂停）——它们的同步调用
> 等待事件结束（延迟有界：≤事件超时 5s），这是可接受的妥协。唯一死锁场景：
> 事件监听器启用手动模式（manualRelease）且等待了其他插件/Worker 提供的、涉及游戏操作的
> 服务——这是反模式，由 5s 超时兜底，不为此牺牲分流设计。
> （对齐 Paper 的 drainDuringWait 全量排空属 K 方案，经权衡不采用。）

### 插件 JS 单线程是支点

每个插件只对应一个 JS 线程（串行处理消息）。事件处理期间，该插件的 JS 线程被事件占住。因此事件线程按**插件**从队列取任务天然正确：事件 handler 的同步调用（`e.player.location`、`event.complete` 等）总是能被事件线程就地消化，不需要暂存、不需要跨插件协调。同时，同一插件的事件天然串行（JS 线程一次处理一条消息），不同插件的事件可并发。

支点正是纯 L 方案成立的依据——事件期间该插件的任务只可能来自 handler，取本插件任务即覆盖了 handler 的全部同步调用；其他插件的任务留给事件结束后的 cycle。

## 架构推论

1. **事件处理只阻塞所属 region**：事件线程自旋期间，该 region 的 tick 停滞（上限为事件超时，默认 5s），其他 region 照常并行运行
2. **跨插件事件并行**：不同插件的 JS 线程互不影响，事件可并发；同插件事件串行（JS 单线程）
3. **事件内同步调用应只访问事件目标**：`e.player.xxx` 这类调用由事件线程就地执行、即时返回；**跨 region 的同步调用**（访问其他实体/世界）会被执行器投递到目标 region——目标 region 空闲则即时执行，恰好也忙于事件则等待直至超时。**推荐事件 handler 内的跨目标操作使用异步 API（`post`）**
4. **同步 API 跨区域调用有延迟**：事件处理期间，同步 API 访问跨区域资源会被投递至目标区域线程执行（下一个 tick 周期，0~50ms）。虽然 Folia 的区域设计带来数据局部性，事件中的跨区域操作相对较少，仍建议事件处理期间优先异步 API
5. **非事件场景的同步调用同样受益于驻留**：调度器贴近热点区域时，同步调用就地执行（微秒级）——循环模式不再受 50ms tick 周期拖累
6. **全局任务（`server.*` 等）事件期间不受影响**：经 Folia 投递到全局 region 执行（全局 region 不参与事件自旋与调度器驻留）
7. **异步任务跨 region 顺序不保证**：Paper 上异步任务在主线程 FIFO 串行（`post(a); post(b)` 顺序保证）；Folia 上跨 region 的异步任务并行执行、完成顺序不定——**有依赖关系的连续操作请用 `await` 串行化**
8. **预算尽重启有 ≤30ms 抖动**：持续负载下同步调用可能遇到单次 ≤30ms 停顿（等待下一个 tick 边界 = 窗口剩余时间），属预算模型固有语义，非异常
9. **事件重入死锁**：事件线程排空队列执行同步任务时，若该任务触发新事件（如 `performCommandSync` → `playerCommand`），嵌套自旋等待 JS 而 JS 正被同步调用阻塞 → 死锁至事件超时（默认 5s，有界兜底，Paper/Folia 均存在）。**事件 handler 内除非逻辑非常简单，否则不要使用同步操作（含属性读写）**——详见 [事件与回调 - 事件重入死锁](events.md#事件重入死锁)

> **已知差异**：
> - `server.getTps` 三个值返回 `null`（Folia 无全局 TPS 概念，插件需自行判断不可用）
> - **Scoreboard 创建受限**：`createObjective` / `createTeam` 返回明确错误（Folia 仅支持读取/修改已存在的 objective/team，`registerNewObjective`/`registerNewTeam` 全部重载抛 `UnsupportedOperationException`）——详见 [Scoreboard API](../api/scoreboard.md)
> - **全局状态写入自动路由**：`world.setTime` / `setStorm` / `setThundering` / `setDifficulty` / `setSpawnLocation` / `setGameRule` 在 Folia 上只能在**全局 region 线程**修改（AsyncCatcher 拦截）——Yeow 运行时已将这些任务自动路由到全局线程，插件无感知差异

## 平台透明

- **上层 API 完全一致**：`yeow-api` 的 Player/World/Event/Command/Worker/fs/http… 在 Paper 与 Folia 上用法零差异；事件字段、命令协议、MiniMessage 文本语义均相同
- **插件包平台无关**：`.yeow.zip` 不含任何平台绑定，同一份插件可直接在 Paper 与 Folia 间迁移
- **差异只在运行时实现**：调度模型、线程模型、任务执行器是平台内部细节，插件作者无需感知；`getEnv()` 的 `platform` 字段可用于区分（`"paper"` / `"folia"`）

## 部署

**与 Paper 完全一致**：

1. 将 Folia 运行时 jar（`yeow-runtime-folia-0.2.0.jar`）放入服务器 `plugins/`
2. 插件包（`.yeow.zip` 或模板 JAR）放入 `plugins/Yeow/`（自动扫描）或 `/yeow load <path>` 动态加载
3. 插件数据、`/yeow` 管理命令、热重载等行为与 Paper 相同

开发模式：`npm run dev` 与 Paper 一致，只需把 `yeow.config.json` 的 `paperJar` 指向 Folia 构建，并用 Folia 运行时 jar 替换 `.yeow/assets/` 中的运行时。
