## Yeow v1（当前）——概念验证

**v1 只是概念验证**：受个人能力与时间所限，无法将 Yeow 的全局设想完整实现，只得割爱择取部分设想，在子领域（Minecraft 服务端开发）内聚焦实现。规划：

### 更完善的 API 和事件覆盖面

扩展 yeow-api 与运行时任务/事件桥的能力边界

### 开发调试工具

增强插件开发与运行时的诊断体验：

- 运行时调试器（断点 / 单步 / 变量查看）——开发模式下使用 Node.js（V8）执行 JS，获得完整的调试器能力
- 可视化工具：调度器任务队列 / 消息队列的实时视图

### Folia 支持

Yeow 运行时尝试适配 [Folia](https://github.com/PaperMC/Folia)

### 优化：任务调度器与事件分发机制

重构任务调度器和事件分发机制：

- 部分解耦 `task` 通道与主线程的绑定
- 对部分不需要在当前 tick 决策的事件（如 `permissionCheck`）引入**异步结果回传**
- 降低主线程的负担

### WASM 原生支持

Yeow 正在尝试引入 **WASM**：

- 解决 JS 在特定场景下**性能不足**的问题
- 探究**高效的互操作方案**（平台层 ↔ WASM 模块）
- 探究**依赖包集成方案**（npm 包携带 `.wasm` 产物，构建期随包打包）
- 为未来的高性能场景做准备

### Yeow v2 —— 全栈模组开发（客户端能力）

Yeow v2 将尝试引入**客户端能力**（全栈模组开发）。在 Yeow 的设想中，模组开发被分为**界限分明的两个部分**——服务端与客户端——因为 Minecraft 本身就是经典的 C/S 模型：

- **服务端**处理游戏逻辑
- **客户端**处理本地资源、画面渲染、音效、按键操作

关键设计：

- **插件的客户端部分与服务端部分跑在不同的 JS 线程上**，二者通过**标准化的网络通信**交流
- **对单人游戏一视同仁**：Minecraft 单人模式本质上是启动了内部的集成服务端——Yeow 提供一种新的方式结束此前模组开发的混乱（逻辑端/物理端割裂），**规避"单人模式正常、放在服务器上就崩溃"**（混淆了客户端专有类）的情况
- **部署即裁剪**：一个模组在服务端上只运行服务端部分，在客户端上只运行客户端部分；单人游戏中，二者在不同的线程中**同时运行**
- **绝不包办**：Yeow 不会尝试做大而全的"包办"（例如允许操作渲染管线），而是提供**基础而常用的接口**（按键监听、HUD 渲染、客户端音效等），底层场景仍需原生开发
- **项目结构**：类似 `server/` 与 `client/` 两目录，开发者分别引入 `@yeow/server-api` 与 `@yeow/client-api`
- **构建产物**：仍为 `.yeow.zip`——**Yeow v1 的插件可视为仅包含服务端部分的模组**

### Yeow Client Lite —— 通用客户端能力

Yeow 在 v1 到 v2 的过渡期间考虑开发 **Yeow Client Lite**（客户端模组）并**标准化规范**，在不同平台提供一致的接口（绘制简单 HUD、监听客户端按键等），供服务端调用：

- 只要一个客户端安装了 Yeow Client Lite，**在任何服务器**中都能享受客户端能力增强（如果存在对应的 Yeow 插件）
- 在 Yeow v1 与 v2 的服务端开发中，可以使用基于 Yeow Client Lite 提供的**通用客户端能力**，而无需专门开发客户端
